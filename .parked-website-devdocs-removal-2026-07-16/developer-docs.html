Developer Docs

The source files in this package ship comment-free, on purpose. Every "why" that used to live as an inline comment now lives in one canonical file: developer_info.md. This page teaches you how to read it.

What is developer_info.md?

Packages/com.vixen.tools/developer_info.md

To keep imports and compiles fast (Unity re-parses every comment on every reload), we strip explanatory comments out of the C# and shader sources and move them into a single reference document. The code stays lean; the reasoning stays recorded. developer_info.md is that record - a comment-for-comment archive, organized so you can jump straight from a line of code to the thinking behind it.

  • One entry per comment. Currently 1,481 entries across 27 source files.
  • First-party only. Our own tools, the VixenWear shaders, and the editor scripts. Vendored third-party includes (LTCGI, AudioLink, AreaLit, Light Volumes) keep their original headers untouched and are never archived here.
  • It is the place new comments go. When you add reasoning to this codebase, you file it here under its structure - not inline in the source.

How to read an entry

Legend

The file is grouped by source file, then by the nearest enclosing code structure (the method / property / field a comment lived in), then listed as individual comments. Here is the raw shape of one group: 

## `Editor/Scene Tools/Placement Tools/FixSceneData.cs`

*7 comment(s).*

### `public static void FixLightingDataAssignment()`
<sub>L27–L42</sub>

- **L27** - Reference the existing lighting data asset for the active scene  <br/><sub>↳ before `var lightingData = Lightmapping.lightingDataAsset;`</sub>
## `path`
File header. The source file this group of comments came from, written as a package-relative path.
*N comment(s).*
Count. How many comment entries this file contributes.
### `signature`
The durable anchor. The enclosing method, property, field, or type the comment belonged to. Code shifts and line numbers drift, but this signature is the stable landmark - search the source for it to find the spot.
<sub>L27–L42</sub>
Line range. The span of original line numbers the comments in this group occupied, as the file stood just before the strip.
- **L27** - text
The comment. L27 is its original line; the text is the comment, verbatim.
↳ before `code`
The location pin. The line of code the comment sat before. You will also see ↳ on `code` - that means it was a trailing comment on the same line as that code.

Reading it in practice: find the ### signature for the method you are in, then match the comment to its ↳ pin to see exactly which statement it described. Treat line numbers as hints (they drift as code changes) and the signature + pin as the real coordinates.

Conventions & the full reference

Read the source of truth
  • Line numbers drift, signatures don't. A line number is where a comment was at strip time; the ### signature is the anchor you search for.
  • before vs on. ↳ before = a comment that preceded the code line; ↳ on = a trailing comment that shared the line.
  • Vendored code is left alone. Third-party shader includes keep their own license and attribution headers - they are never moved into this reference.
  • Plain text. The reference uses plain punctuation throughout for clean diffs and grep-friendly searching.
